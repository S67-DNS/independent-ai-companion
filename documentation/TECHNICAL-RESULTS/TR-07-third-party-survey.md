# TR-07 开源零件调研与归档（设计参考）

**状态**：已实现并验证（**仅归档完整性**）；对本系统而言属「仅有研究设想」的输入
**证据性质**：只读元数据核验 + 文件级归档哈希；**未安装、未运行、未验证可运行性**

## 1. 要解决的问题

状态持久化、进程重启恢复、事件日志 / 快照 / 游标、租约与崩溃接管，这些能力不必从零设计。但直接引入框架会带入不必要依赖，因此需要先把可复用零件**定点归档并核验**，再决定最小必要集合。

## 2. 采用的技术方案

- 按能力域定点归档（不整仓引入）：状态机持久化与恢复、轻量持久化调度、事件溯源 / 快照、写入队列与会话栅栏、投递队列与发送租约、记忆来源与 CAS；
- 每项固定版本 / tag / commit，保留许可证、源码相对路径、测试与 SHA-256 清单；
- 对无法核实仓库地址、tag 或源码 commit 的包，**不猜测、不替换**，只保留可验证的发布包并标记「源码对应关系待核实」；
- 版本号与实际发布记录冲突时，记录为**版本纠错**而非升级。

## 3. 实际完成的工作

- 状态机库（MIT）：持久化快照与从快照重建 Actor，含嵌套 Actor 恢复测试；
- 轻量调度库（MIT）：内置 SQLite 的原子领取、租约心跳、僵尸租约回收、运行标识幂等、存储契约测试；
- 事件溯源 / SQLite 快照包：发布包与完整性记录齐全，源码对应关系待核实；
- 某开源 Agent 的三类机制（MIT）：写入队列与会话栅栏、投递队列与发送租约 / 结果未知、记忆来源与 CAS，按固定 commit 逐文件归档并做字节级来源证明；
- 广域生态检索：区分完整产品 / 框架 / 插件 / 研究原型 / 概念项目，标记许可证不明、停止维护、疑似残缺或引流项目。

## 4. 可公开的验证证据

- 归档包逐文件 SHA-256 清单与复验通过记录；
- 固定 commit 的逐文件 blob 哈希与仓库内容接口比对通过记录；
- 版本号纠错、tag 命名差异、源码对应关系待核实等异常均有书面记录；
- 下载失败的产物被重命名为不完整文件并显式标记「不可用、请勿安装」，没有冒充完整归档。

## 5. 当前限制

- **这些是第三方设计参考，未直接集成为本系统核心**，也不为其成熟度背书。
- 未安装、未构建、未运行其测试、未验证可运行性；归档完整性不等于可用性。
- 广域候选池仅做元数据核验，不代表推荐清单；不公开与本项目关联的选型结论或内部评分。
- 许可证核对结果见 `LICENSES/THIRD-PARTY-LICENSES.md`；存在许可证不明与源码对应关系待核实项。

## 6. 必须随引用一同保留的技术风险

- **写入队列是进程内调度，不是跨进程安全锁**；会话栅栏的核心是持久化写入所有权与事务内 fresh read，不携带期望栅栏的兼容写路径仍可能放行，不能描述为「所有旧写入都被自动阻止」。
- **`已开始发送尝试` 不代表渠道已收到消息**；`结果未知` 必须保留不确定性，未取得可靠渠道对账结果不得盲目重发，不能声称端到端恰好一次；入站去重是进程内缓存而非跨进程持久去重。
- **来源信息必须与当前文件内容一致**；Shell / 执行工具直接改文件可绕过写侧来源校验；CAS、来源分类与内容哈希验证不可混为一个概念。

## 7. 尚未解决的问题

- 最小必要组件集合的选择判据（避免「为使用框架而引入依赖」）。
- 如何把设计参考转化为自有实现而不带入其结构性缺陷。
- 单维护者、pre-1.0、发布频繁等风险的长期跟踪。
