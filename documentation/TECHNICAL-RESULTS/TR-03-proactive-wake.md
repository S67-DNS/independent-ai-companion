# TR-03 主动唤醒 / 潜水机制与重启恰好一次（F1）

**状态**：**已实现但验证不完整**
**证据性质**：隔离环境实际执行，但唤醒回合使用 **Mock Runtime**
**明确边界**：主动出站保持关闭；未发送真实消息；未连接真实渠道；**不得描述为「真实自主生活已验证」**

## 1. 要解决的问题

只在收到消息时才行动的系统，没有基于时间的自主状态。要让主体拥有「忙碌 / 待命 / 到期唤醒」这类长期状态，至少要解决三件事：状态与定时任务必须落盘、进程重启不能丢也不能重复执行、唤醒后要能驱动一个完整回合并带回记忆连续性。

## 2. 采用的技术方案

- **状态链**：回复 → 待命 → 定时注册 → 到点唤醒 → 执行回合 → 记忆连续性检查。
- **开关拆分与落盘**：主动能力开关与唤醒配置独立持久化，写配置不丢字段。
- **持久化定时任务**：唤醒任务带代数（generation）与到期时间写入磁盘，重启后按标识去重。
- **失败恢复**：首次回合失败时登记重试调度，第二次成功完成；重启前后待处理任务标识保持一致且只执行一次。
- **连续性哨兵**：在回合上下文中注入唯一测试标记与主体身份块，验证第二回合是否带回了身份与记忆。

## 3. 实际完成的工作

- 开关拆分、落盘、重启、控制权组合验证；
- 定时注册、到点唤醒事件、唤醒回合链路；
- 唤醒配置持久化与「写配置不丢字段」；
- 出站隔离与主动残留核查；
- 备份与回滚演练（副本）；
- 与真实执行运行时集成的可行性调查与分阶段实施。

## 5. 当前限制

- **唤醒回合使用 Mock Runtime，不是真实模型调用**。我们验证的是「机制」，不是「自主生活」。
- 主动出站开关保持关闭，未发送真实消息；唤醒回合只在内部执行，**不产生用户可见回复**——已验证的是内部状态转换与回合执行链路，不是完整交流闭环。
- 上下文中的身份块与测试哨兵是**确定性测试构造**，不是从长期记忆自主召回的结果。
- 只改动隔离工作树，未触碰正式运行链路。
- 状态转换的触发阈值在测试中被调小以便快速验证，不能据此推断长期运行表现。

## 6. 尚未解决的问题

- 目标的产生、优先级、暂停与放弃（当前只有「定时被唤醒」，没有「有目标地行动」）。
- 反思与经历闭环：行动结果如何成为新的记忆，链条如何关联与重放。
- 唤醒决策的主体归属与可解释性。
- 长期运行下的时钟漂移、任务堆积与唤醒风暴。
- 在真实 `[MODEL_PROVIDER]` 下的唤醒回合成本与行为一致性。
