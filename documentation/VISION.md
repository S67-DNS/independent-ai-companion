# 技术愿景：要解决的问题，以及不打算做的事

## 1. 起点：把「主体」从「组件」里拆出来

多数 AI 助手系统把身份、记忆、模型和执行环境揉在一起：换一个模型，说话方式就变了；换一个运行时，历史就断了；换一个接入渠道，权限边界要重写一遍。这不是某个实现的 bug，而是**所有权没有被明确划分**。

我们尝试的划分是：

| 关注点 | 归属 | 不应归属 |
|---|---|---|
| 身份、人格原则、关系与长期连续性 | `[CORE_ENTITY]` 核心 | 基础模型、Agent Runtime、通信渠道 |
| 权威记忆 | 核心授权写入，独立持久化 | Runtime 自带的记忆插件、渠道 |
| 一回合内的执行、工具调用、会话状态 | Agent Runtime | 主体身份的真相源 |
| 文本生成 | `[MODEL_PROVIDER]` | 身份与记忆的所有者 |
| 消息收发 | `[COMMUNICATION_CHANNEL]` 适配器 | 身份与记忆的所有者 |

由此得到几条硬约束：

1. **身份与基础模型解耦**：模型只是可替换能力，不是身份的持有者。
2. **身份、人格、记忆、运行环境分离**：四者各自有独立的真相源与生命周期。
3. **Session 连续性 ≠ 长期记忆**：前者是一次执行的上下文恢复，后者是跨主体、跨时间、带来源与版本的可信事实。
4. **平台只是入口和出口**：网关负责权限判定与投递，不拥有主体。
5. **核心稳定，能力插件化，模型与平台可替换**。

## 2. 我们真正卡住的地方

### 2.1 记忆「召回」不等于「注入」

一个检索接口返回了相关文本，只证明检索层工作。真正难的是：这段文本**是否进入了模型实际收到的请求体**、放在哪个角色与位置、带着什么来源与权威级别、以及**有没有把别的主体的记忆混进来**。

我们的隔离集成里已经能做到把身份与记忆文本送进模型请求体，但现有证据存在自证成分：注入标记由同一实现计算，缺少请求体中 `messages[]` 的角色/位置证明与关联 ID，也没有构造「不召回无关主体记忆」的反向用例。**这一项我们明确标为未解决。**

### 2.2 多会话、多 Agent 下的记忆主体归属

按会话键隔离能防串话，但回答不了「一条记忆属于谁」。当多个 Agent 共享一个全局记忆层时，读侧要证明主体归属，写侧要证明授权来源，两者都需要可验证的来源链，而不是靠目录约定。我们目前的 L3 隔离依赖插件遮蔽，且实测发现过遮蔽只生效一半——**这是结构性缺陷，不是配置疏漏**。

### 2.3 写入安全与「不确定」状态

并发写入、租约过期、进程崩溃、外部工具直接改文件，都会让「这条记忆是不是当前主体写的」变得不可判定。我们采用写入所有权 + 预约 + 期望哈希 + 内容寻址 + 审计，但仍要诚实承认：

- 进程内队列不是跨进程安全锁，跨进程所有权必须落库并在事务内 fresh read；
- 「已开始发送尝试」不等于渠道已收到消息；
- 「发送结果未知」必须保留不确定性，**不得自动重放**，更不能声称端到端恰好一次；
- 外部工具绕过写侧校验直接改文件，仍可能让来源信息与当前内容不一致。

### 2.4 长期运行的自主性

主动唤醒、定时状态转换、失败重试、重启后恰好一次执行，这些机制在隔离环境里跑通了。但「唤醒后要做什么」的目标管理、反思与经历闭环，仍只到设计阶段。我们用 Mock Runtime 验证的是**机制**，不是**自主生活**。

## 3. 我们不打算做的事

- 不把这份资料包装成成熟产品，不用「数字生命已实现」作为宣传点。
- 不因为某个框架流行就把它引入核心；最小必要组件优先。
- 不把 Mock、静态检查、历史测试记录写成真实运行验证。
- 不为了案例生动而使用任何真实私人聊天记录、经历或人物设定。
- 不发布任何可能反推私人主体的信息，包括「时间 + 账号 + 关系 + 事件」的组合线索。

## 4. 我们希望共同推进的

独立完成于模型的长期身份连续性；多层记忆的主体隔离与可信注入；自动记忆形成与来源追溯；长期反思与状态更新；可替换模型与 Runtime 的统一接口；记忆、行动与经历之间的闭环；以及长期运行中的安全、权限与可恢复性。

哪些已经有实现基础、哪些还只是设想，见 `ROADMAP.md` 与 `PROJECT-STATUS.md`。
