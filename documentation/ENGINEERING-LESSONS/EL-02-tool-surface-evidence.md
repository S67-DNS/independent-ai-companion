# 方法学修正：静态读配置证明不了「模型实际收到什么」

## 当时的做法

要验证「记忆工具是否被遮蔽」，第一反应是读插件配置、看禁用项是否写上、再检查注册清单。结论一度倾向于「已遮蔽」。

## 问题在哪

配置里写了禁用，和模型实际收到的 `tools` 数组是两件事。装配链路上有作用域覆盖、插件加载顺序、preset 差异、工具重注册，任何一环都可能让禁用项重新出现。静态推断只能证明**意图**，不能证明**结果**。

## 换方法

在隔离实例里跑真实回合，把 **Mock 收到的完整请求体**落盘，直接检查 `tools` 数组与装配后的 `messages`。结果推翻了原结论：一组工具确实消失，另一组全局记忆工具（含作用域设置）仍然暴露。**遮蔽只生效一半。**

## 第二个坑：取证样本本身会骗人

首轮按「请求体包含唯一标记」筛选样本，结果抓到的是**会话标题生成请求**——它把用户原话嵌进 JSON 转发，且 `tools = 0`。用它来判断工具面，会得出「没有任何工具」的荒谬结论。

修正判据：只取 `tools > 0` 且带标记的真实 Agent 回合请求。

## 可迁移的教训

- 「模型实际收到什么」这类问题，证据必须来自**实际请求体**，不能来自配置或注册清单。
- 同一链路上常有多种非业务请求（标题生成、健康检查、探测），取证前必须先分类样本。
- 负面结论同样有价值：这次发现的是结构性缺陷（L3 靠插件遮蔽），不是配置疏漏；把它写成「已修复」才是真正的失真。
- 工具面清单随运行时版本变化，一次性结论不能长期有效。
