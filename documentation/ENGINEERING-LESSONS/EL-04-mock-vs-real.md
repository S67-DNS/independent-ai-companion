# 口径修正：Mock、静态检查、历史记录与「真实运行」不是一回事

## 为什么单独写一篇

在整理成果清单时，最容易发生的失真不是编造数据，而是**把不同强度的证据混成一句「已验证」**。我们因此把口径固定下来，并在所有文档中一致使用。

## 六档证据

| 级别 | 含义 | 能支撑什么 |
|---|---|---|
| 隔离环境真实执行 | 真实进程、真实数据库、真实请求体，但无真实渠道与外部模型 | 机制确实工作 |
| 隔离环境 Mock | 链路真实，模型/渠道由确定性替身承担 | 链路顺序与失败处理 |
| 静态检查 | 源码守卫、契约比对、配置检查 | 结构上不存在旁路 |
| 历史测试记录 | 过去某轮的 N/N 回归，本轮未重跑 | 「当时没坏」，仅此而已 |
| 只读生产观察 | 连续采样与前后快照，未改动任何数据 | 现象存在，机制不一定 |
| 未执行 | 明确没跑过 | 什么都不支撑 |

## 三个具体的失真点

1. **「234/234 通过」被当成整体集成通过**：那是隔离施工期的历史回归，该轮只修了路径绕过，没有重跑整体集成。
2. **「唤醒回合 PASS」被读成自主生活已实现**：唤醒回合用的是 Mock Runtime，主动出站保持关闭，上下文中的身份块是确定性测试构造而非自主召回。
3. **「记忆文本进入请求体」被读成记忆闭环成立**：注入标记由与注入同一实现计算，属**自证**；缺请求体中角色/位置证明、关联 ID，也没有「不召回无关主体记忆」的反向用例。

## 我们据此采用的写法

- 每项成果写明证据性质与执行环境，不写笼统的「已验证」。
- 明确列出**未执行项**，而不是省略：跨进程双写集成态重放、「结果未知」状态集成态重放、更换 Provider / Runtime、无关主体记忆反向用例。
- 独立复核结论如实写成 `PASS WITH FIXES`，不修饰成 `PASS`。
- **不把多个局部 PASS 拼接成整体 PASS**。

## 给后来者的建议

如果只从这份资料里带走一条，带走这条：**先问证据是哪一档，再问结论成立到什么范围。** 一个准确的负面结论，比一个漂亮但越界的正面结论有用得多。
