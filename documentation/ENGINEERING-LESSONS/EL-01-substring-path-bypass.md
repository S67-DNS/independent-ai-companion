# 失败方案：用子串匹配做路径安全判定

## 当时的做法

判断「工具要写的文件是否落在权威路径内」，直接用目标字符串的包含关系：`haystack.includes(root)`。看起来简洁，写起来也快。

## 实际后果（三个缺陷同时存在）

1. **相对路径绕过**：`../memory/x` 这种相对路径不包含权威根的绝对拼写，判定为「不在权威路径内」→ 放行。方向是 **fail-open**：没匹配上就放行，这是安全判定里最危险的默认值。
2. **相似目录误杀**：名为 `memory-evil` 的普通目录因为字符串相似被拒绝，正常写入失败。
3. **目录联接绕过**：工作区内创建指向权威目录的联接后，经联接的相对路径同样绕过判定。

## 修正

改为按运行时真实文件语义做**解析后比较**：

- 读取工具调用的**物化参数**（`file_path` / `path` 等），不用原始文本；
- 以会话工作目录为基准，与运行时自身的路径解析同源；
- 解析后再与权威根比较，覆盖相对路径、路径组合、联接与软链接越界；
- 默认改为 **fail-closed**：判定失败的写入一律拒绝。

## 验证方式（防止修复过头）

不只测「该拒绝的被拒绝」，也测「该放行的仍放行」：相对写、组合写、联接写被拒绝且无新文件；相似目录的普通写正常执行。单元矩阵 21/21、隔离真实运行时用例 7/7、全量回归 234/234 保留原有安全行为。

## 可迁移的教训

- **安全判定的默认值必须是拒绝**，不是放行。
- 路径安全不能做字符串判断，必须做语义解析；且解析基准要与执行方一致，否则两边理解不同就是新的绕过面。
- 修复安全缺陷时，反向用例和正向用例同等重要；只加拒绝规则，容易把合法路径一起堵死。
- 静态弱点被独立只读审查指出后，**改实现而不是改文档**。
