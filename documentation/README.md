# [PROJECT_NAME] — 技术探索资料

> **这不是产品发布。**
> 这是一份关于 AI 身份连续性、长期记忆、Agent 架构与自主运行机制的**未完成技术探索记录**。
> 我们不宣称已经实现完整数字生命，不以成熟度作为宣传重点，不隐瞒失败，不夸大成果。

## 我们想找谁

如果你关心下面这些问题，这份资料可能是为你准备的：

- 一个 AI 主体的身份，能不能不依附于某一个基础模型？
- 长期记忆如何形成、检索、注入和更新，而不只是「存了再读回来」？
- 多个会话、多个 Agent 并行时，一条记忆究竟属于谁、谁能写、谁能信？
- Session 结束之后，主体连续性靠什么维持？
- 模型 Provider 与执行 Runtime 可替换，会不会破坏身份与记忆？
- 出站消息、权限、幂等、回执与「发送结果未知」状态该如何建模？
- 主动唤醒、反思与目标行动，距离一个可信的闭环还有多远？

我们希望找到真正对这些**尚未解决的问题**有兴趣的开发者与研究者，一起研究，而不是来「体验一个成品」。

## 状态约定

每项成果都标注以下四种状态之一，不做模糊处理：

- **已实现并验证** — 有隔离环境下的实际执行证据，且证据类型被明确写出。
- **已实现但验证不完整** — 代码存在，但证据是 Mock、局部链路，或缺关键反向用例。
- **已完成设计，尚未实施** — 有设计与只读调查结论，没有端到端实现。
- **仅有研究设想** — 尚无实现或设计定稿。

> **重要**：本资料严格区分「Mock 测试」「隔离环境真实执行」「静态检查」「历史测试记录」与「未执行」。
> 局部链路通过**不**写成完整闭环通过；历史测试记录**不**等于本次集成通过。

## 参与方式

本仓库为技术探索资料的公开归档，供开发者与研究者阅读、复核与讨论。

合适的参与方式按优先级是：

1. 指出架构中不成立的地方、遗漏的依赖与无法实现的验收项；
2. 就某个具体未解决问题提供可复现的实验设计或反例；
3. 讨论长期记忆主体隔离、可信注入、来源追溯与可替换接口的通用方案。

我们特别欢迎**否定性结论**：哪个设计假设站不住、哪条证据其实自证、哪个验收项在当前架构下无法实现。
